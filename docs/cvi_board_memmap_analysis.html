§概述

cvi_board_memmap.h 是一份 内存映射（Memory Map）头文件，定义了 DRAM 中各功能区段 （ATF/OpenSBI、RTOS、ION 多媒体缓冲、Bootlogo、u-boot 运行地址等）的起始地址与大小。 它被 u-boot、kernel、FSBL、RTOS 等多个组件共享引用。

其生成的本质是：一个共用的 Python 布局脚本 build/boards/default/memmap/memmap.py 读取当前构建的 .config，按公式算出每个区段的地址， 再由转换器 mmap_conv.py 导出成 .h / .conf / .ld 三种格式。

对于 cv1841（128MB）、cv1842（256MB）、 cv1843（512MB） 三种型号， 它们走的是完全相同的脚本和算法，唯一的差别是各自 defconfig 里写死的一个值： CONFIG_DRAM_SIZE。换句话说——

核心结论：芯片型号本身不直接参与 cvi_board_memmap.h 的生成。 真正的输入是 CONFIG_DRAM_SIZE（128/256/512 MB），它由所选 board 的 defconfig 决定。memmap.py 用同一套公式，把这个 DRAM 大小代入，得到各型号专属的地址表。

mmap.mk 触发规则

四种产物各有一条规则，全部依赖同一个 memmap.py 与 .config：

BOARD_MMAP_PATH := ${BUILD_PATH}/boards/default/memmap/memmap.py
MMAP_CONV_PY   := ${BUILD_PATH}/scripts/mmap_conv.py
CVI_CONFIG_FILE:= ${BUILD_PATH}/.config

# 头文件：给 C 代码用
${CVI_BOARD_MEMMAP_H_PATH}: ${BOARD_MMAP_PATH} ${MMAP_CONV_PY} ${CVI_CONFIG_FILE}
	@mkdir -p $(dir $@)
	@${MMAP_CONV_PY} --type h $< $@

memory-map: ${CVI_BOARD_MEMMAP_H_PATH} ${CVI_BOARD_MEMMAP_CONF_PATH} \
            ${CVI_BOARD_MEMMAP_LD_PATH} ${CVI_BOARD_MEMMAP_TXT_PATH} FORCE
注意：BOARD_MMAP_PATH 在 Makefile 中是写死的 boards/default/memmap/memmap.py——无论哪款芯片都用这一个脚本。 芯片差异完全经由 .config 注入，而不是切换脚本。

②mmap_conv.py：转换器

mmap_conv.py 本身不含任何地址常量，它是一个通用的「Python 类 → 头文件」转换器。 工作分三步：动态加载、反射提取、格式化输出。

第一步：把 memmap.py 当模块加载并实例化

# 用 importlib 动态加载 memmap.py
spec = importlib.util.spec_from_file_location(map_name, map_file_path)
mmap_module = importlib.util.module_from_spec(spec)
spec.loader.exec_module(mmap_module)

# 关键：创建实例以执行 __init__（这一步才会读 .config 并改写地址）
_ = mmap_module.MemoryMap()
mlist = parse_mmap(mmap_module)
为什么要实例化？因为 memmap.py 里大量地址是在 __init__ 中根据 .config 用 setattr(MemoryMap, ...) 动态覆盖类属性的。 不 MemoryMap() 一下，拿到的就只是「510MB 默认布局」的占位值。

属性提取与排序

parse_mmap() 用 dir() 反射遍历类的所有属性，只保留数值型，并统一加前缀：

for attr in dir(mmap):
    if attr.startswith("_"):          # 跳过 _no_prefix 等私有/魔术属性
        continue
    value = getattr(mmap, attr)
    if callable(value) or not isinstance(value, (int, float)):
        continue                     # 跳过方法 / 非数值
    if attr not in no_prefix:        # _no_prefix 列表里的不加前缀
        attr = "CVIMMAP_" + attr
    mlist[attr] = int(value)            # 一律转 int（float 也截断）
  • 所有项默认加上 CVIMMAP_ 前缀（如 DRAM_SIZE → CVIMMAP_DRAM_SIZE）。
  • 例外：_no_prefix = ["CONFIG_SYS_TEXT_BASE"]——这个名字直接给 u-boot 用，不加前缀。
  • 最后按 名字字母序 排序（先按值，再按键，键序优先），所以 .h 里条目是字母排列的。

生成 .h 的格式

mmap_to_h() 为每一项生成一行 #define，并附上人类可读的容量注释； 头文件保护宏用一个随机数生成：

def mmap_to_h(mlist):
    mlist = ["#define {0:s} {1:#x}  /* {2} */".format(a, v, int_to_si(v))
             for a, v in mlist.items()]
    r = random.randint(0x80000000, 0xFFFFFFFF)   # 随机 include guard
    return "#ifndef __BOARD_MMAP__{0:08x}__\n#define ...\n{1}\n#endif"

这解释了实际文件第 1 行的 #ifndef __BOARD_MMAP__a5289037__—— a5289037 就是那个随机数，每次重新生成都会变。

int_to_si() 负责把地址换算成注释里的 offset 85.0MiB 这种描述： 先减掉 0x80000000（DRAM 基址）得到偏移，再换算 KiB/MiB。

③memmap.py：地址布局算法

这是真正决定布局的文件。结构上分两部分： 类体内的静态默认值（按 510MB 写的占位布局）+ __init__ 里依据 .config 的动态改写。

静态默认布局（类体）

类体里先用常量公式排好所有区段。注意默认 DRAM_SIZE 是 510MB，这只是占位——真实值在 __init__ 被覆盖。

class MemoryMap:
    _no_prefix = ["CONFIG_SYS_TEXT_BASE"]
    DRAM_BASE = 0x80000000
    DRAM_SIZE = 510 * SIZE_1M          # 占位，会被 .config 覆盖

    MONITOR_ADDR  = DRAM_BASE              # ATF/OpenSBI 在 DRAM 头部
    ATF_SIZE      = 640 * SIZE_1K
    OPENSBI_SIZE  = 640 * SIZE_1K
    FSBL_C906L_START_ADDR = DRAM_BASE + ATF_SIZE   # C906 RTOS 起点

    # RTOS 各子区段顺序叠放：SYS → LOG → SHARE_MEM → SHARE_PARAM ×2 → PQBIN → LOGO
    RTOS_SYS_SIZE = 4 * SIZE_1M
    ...
    RTOS_ION_SIZE = 100 * SIZE_1M
    RTOS_ION_ADDR = DRAM_BASE + 256*SIZE_1M - RTOS_ION_SIZE   # 注意写死 256M！见 §④

    ION_SIZE  = 6 * SIZE_1M
    ION_ADDR  = RTOS_ION_ADDR - ION_SIZE                      # ION 紧贴 RTOS_ION 之下
    BOOTLOGO_ADDR = ION_ADDR + ION_SIZE - BOOTLOGO_SIZE       # Bootlogo 在 ION 尾部

    UIMAG_ADDR = DRAM_BASE + 20*SIZE_1M             # kernel 镜像装载缓冲
    CONFIG_SYS_TEXT_BASE = DRAM_BASE + 64*SIZE_1M - 8*SIZE_1M  # = 0x83800000

__init__：依据 .config 动态改写

实例化时，先用 read_kconfig() 把 .config 解析成字典，再 setattr 逐个覆盖关键属性。 这是芯片差异真正生效的地方：

def __init__(self):
    config_file = os.path.join(os.environ['BUILD_PATH'], '.config')
    kconfig = self.read_kconfig(config_file)

    dram_size      = kconfig.get('CONFIG_DRAM_SIZE', '')      # ← 三款芯片唯一不同处
    ion_size       = kconfig.get('CONFIG_ION_SIZE', '')
    rtos_sys_size  = kconfig.get('CONFIG_RTOS_SYS_SIZE', '0x0')
    rtos_ion_size  = kconfig.get('CONFIG_RTOS_ION_SIZE', '0x0')
    enable_alios   = kconfig.get('CONFIG_ENABLE_ALIOS', 'n')

    setattr(MemoryMap, 'DRAM_SIZE',         int(dram_size, 16))   # 覆盖占位 510M
    setattr(MemoryMap, 'KERNEL_MEMORY_SIZE', int(dram_size, 16))   # kernel 可见全部 DDR
    ...
    # RTOS_ION 钉在 DDR 末尾（= 基址 + DRAM_SIZE - RTOS_ION_SIZE）
    setattr(MemoryMap, 'RTOS_ION_ADDR',
            MemoryMap.DRAM_BASE + MemoryMap.DRAM_SIZE - MemoryMap.RTOS_ION_SIZE)
    # ION 紧贴 RTOS_ION 之下，向低地址生长
    setattr(MemoryMap, 'ION_ADDR', MemoryMap.RTOS_ION_ADDR - MemoryMap.ION_SIZE)
    ...
    # 一系列 assert 检查区段不重叠 / 不越界
    assert MemoryMap.CONFIG_SYS_TEXT_BASE >= MemoryMap.UIMAG_ADDR + MemoryMap.UIMAG_SIZE
布局的「锚点」逻辑：低地址端（Monitor/RTOS/u-boot 镜像缓冲）是固定的； 高地址端（RTOS_ION、ION、Bootlogo）则钉在 DDR 末尾往回长。 DRAM 越大，这块「尾部多媒体区」整体上移——这正是三款芯片地址表唯一拉开差距的部分。

defconfig → .config 的流程

用户执行 defconfig cv1842hp_wevb_0014a_emmc 时：

function defconfig() {            # build/common_functions.sh:424
  board=$1
  chip_arch=$(boards_scan.py --get-chip-arch --board_name ${board})   # → cv184x
  _call_kconfig_script "defconfig" \
      "boards/${chip_arch}/${board}/${board}_defconfig"
}

_call_kconfig_script 进而调用 scripts/defconfig.py， 用 kconfiglib 把板级 defconfig 叠加到顶层 Kconfig（其中 Kconfig.memmap 定义了 DRAM_SIZE 等条目），生成最终 build/.config。 之后 make memory-map 就以这份 .config 为唯一数据源。

顶层 Kconfig.memmap 给出的是兜底默认（当 defconfig 未指定时）：

config DRAM_SIZE
    hex "DRAM size"
    default 0x20000000          # 缺省 512MB；板级 defconfig 会覆盖它

⑦关键发现与注意事项

1. 头文件保护宏是随机的

__BOARD_MMAP__a5289037__ 中的 8 位十六进制由 random.randint 生成， 每次重新生成 .h 都会变。这意味着该文件不适合纳入「内容稳定性」校验， 且不应手工编辑——它是构建产物。

2. 单一脚本 + 配置注入，而非每芯片一份脚本

整个 CV184x 系列共用 boards/default/memmap/memmap.py。 新增一个 DRAM 容量的板子，通常只需在其 defconfig 改 CONFIG_DRAM_SIZE， 无需改脚本。这是该设计最值得借鉴之处。

3. 存在「未接线」的备用布局脚本

仓库里还有 boards/default/memmap/cv184x/memmap_ddr_128mb.py 与 memmap_ddr_64mb.py，是为小内存单独写的整套布局（128MB 版甚至重排了 RTOS_ION/ION 顺序）。但当前 mmap.mk 并未引用它们—— 构建始终走默认 memmap.py。它们更像是历史遗留或正在进行的重构分支。

4. ⚠ 128MB 在默认脚本下的潜在越界

用默认 memmap.py 代入 cv1841 / 128MB 时， 算出的 ION_ADDR = 0x7d500000，低于 DRAM_BASE (0x80000000)——即落到了 DDR 之外。 因为 ION(75M)+RTOS_ION(96M)=171M 已超过 128MB 的可用尾部空间。 由于 cv1841 的 defconfig 同时 CONFIG_ENABLE_ALIOS=y， __init__ 末尾的断言 assert ION_ADDR >= FSBL_C906L_START_ADDR + RTOS_SYS_SIZE 会失败。

含义：128MB 的板子若真要用默认脚本，必须在其 defconfig 调小 ION_SIZE/RTOS_ION_SIZE，或切换到那份专用的 memmap_ddr_128mb.py（即把它接进 mmap.mk）。 这是分析三款芯片时最需要留意的边界条件——256MB / 512MB 不存在此问题。

5. float 截断

个别尺寸（如 64MB 版的 ION_SIZE = 26.5*SIZE_1M）是浮点， 但 parse_mmap 最终 int(value) 截断，.h 里都是整数地址，不会出现小数。
