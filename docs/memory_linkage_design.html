§需求与目标

在 Memory 页面修改物理内存映射配置时，应联动写回 SDK build 目录下的相关配置； 同时，“校验内存”的职责是防止改动造成内存区段互相踩踏（overlap / 互踩），在写入前堵住非法布局。

目标 A · 配置联动

页面上对 ION / RTOS_ION / RTOS_LOGO 等区段大小的修改， 一键同步进 build/boards/cv184x/<chip>/<chip>_defconfig 与 build/.config， 最终经构建链路反映到 cvi_board_memmap.h。

目标 B · 防互踩校验

导出前先做两层校验：① 区段地址重叠检测；② 引导阶段的布局约束检测。 任一不过即阻断导出，避免把会导致多核内存互踩的配置写进 SDK。

一句话设计：编辑 → 级联重算 → 校验（防互踩）→ 通过才写 SDK → 构建时再生成 .h。 校验是写入的前置闸门，联动是校验通过后的落盘动作。

③联动写入设计

写哪些文件、哪些字段

export_memory_defconfig(regions, sourcePath, chipType) 当前写两处文件、三个字段（取自对应区段的 size）：

目标文件写入字段取值来源
build/boards/cv184x/<chip>/<chip>_defconfig CONFIG_ION_SIZE
CONFIG_RTOS_ION_SIZE
CONFIG_RTOS_LOGO_SIZE		 region ION.size
region RTOS_ION.size
region RTOS_LOGO.size
build/.config 同上三项 与 defconfig 保持一致（命中则改、未命中则追加）
 
// memory.rs —— 命中即改，未命中追加（幂等写入）
for line in lines.iter_mut() {
    if line.starts_with("CONFIG_ION_SIZE=")       { *line = format!("CONFIG_ION_SIZE=0x{}", ion_size_hex); found_ion = true; }
    else if line.starts_with("CONFIG_RTOS_ION_SIZE=") { *line = format!("CONFIG_RTOS_ION_SIZE=0x{}", rtos_ion_size_hex); ... }
    else if line.starts_with("CONFIG_RTOS_LOGO_SIZE="){ ... }
}
if !found_ion { lines.push(format!("CONFIG_ION_SIZE=0x{}", ion_size_hex)); }   // 追加兜底
设计要点：只写“尺寸（SIZE）”而不写“地址（ADDR）”。因为各区段地址在 SDK 侧由 memmap.py 按尺寸+DRAM_SIZE 自动推算（地址是派生量）。前端改地址只为预览，落盘只需尺寸—— 这与关联文档里“高地址区段钉在 DDR 末尾回推”的算法天然契合。

前端级联联动（写盘前的本地重算）

memoryStore.updateRegion 复刻了 memmap.py 的依赖关系：改一个区段会自动重算关联区段， 保证页面所见即将要落盘的逻辑：

改动区段联动效果
RTOS_IONend 钉死在 256M 边界 → start = 边界 - size；并推动 ION 及其子区段下移
IONend = RTOS_ION.start → start = end - size；同步带动 H26X_BITSTREAM / H26X_ENC_BUFF / ISP_MEM_BASE 共享起始地址
普通区段仅 end = start + size 重算
注意（缺口）：级联里 256M 边界 = 0x90000000 是写死的。 对 cv1841(128MB) / cv1843(512MB) 边界应为 0x88000000 / 0xA0000000。 本方案建议把边界改为 baseAddr + DRAM_SIZE(chipType)，与关联文档结论对齐。

改动如何最终抵达 cvi_board_memmap.h

导出命令只负责改 config，.h 不在此刻重写。真正的再生成发生在 SDK 构建时：

# 用户在 SDK 中执行（或由本工具后续封装一键触发）
$ defconfig cv1842hp_wevb_0014a_emmc   # 已被我们改过的 defconfig → 生成 .config
$ make memory-map                       # memmap.py 读 .config → 重算地址 → 写 cvi_board_memmap.h
解耦的好处：本工具不复制 SDK 的地址算法，只喂“尺寸输入”，把“地址推算 + 断言”交还给 SDK 权威脚本 memmap.py，避免两套算法漂移。增强建议见 §⑦：可选地封装一键 make memory-map。

④校验设计：防止内存互踩

“校验内存”=validate_memory，由两步串联组成，任一失败即返回 Err，前端据此阻断：

#[tauri::command]
pub fn validate_memory(regions: Vec<MemoryRegion>) -> Result<(), String> {
    validate_memory_layout(&regions)?;       // ① 重叠 + 基址（防互踩主力）
    validate_memory_constraints(&regions)?;  // ② 引导阶段布局约束
    Ok(())
}

① 重叠检测（互踩核心）

  • 过滤掉 size==0 的占位区段（不参与，与 C++ 源逻辑一致）。
  • 按 start_address 升序排列，逐对检查相邻区段。
  • 重叠判据：cur.end > next.start && next.end > cur.start → 硬错误，报出互踩的两个区段名。
  • 附加：所有非零区段 start >= 0x80000000（不得低于 DRAM 基址）。
if check_memory_overlap(current, next) {
    return Err(format!("内存重叠检测：区域 {} 与 {} 存在重叠", current.name, next.name));
}
这就是“防互踩”的落点：两个区段地址范围相交 = 运行时多核会写到同一段物理内存 → 画面花屏 / RTOS 崩溃 / 内核 oops。校验在写盘前拦下这种配置。

② 约束检测（引导阶段不越界）

除了两两不重叠，还需满足启动各阶段的相对位置关系（默认 ENABLE_ALIOS）：

#约束含义
1RTOS_ION ≥ FSBL_C906L_START + RTOS_SYS_SIZERTOS 多媒体区不得压到 RTOS 系统区
2RTOS_COMPRESS_BIN ≥ UIMAG + UIMAG_SIZE压缩镜像区不得压到内核装载缓冲
3(256M边界 − RTOS_ION_SIZE − ION_SIZE) ≥ FSBL_C906L_START + RTOS_SYS_SIZEION+RTOS_ION 合计不得吃穿 RTOS 系统区

约束 3 失败时返回详细的计算过程提示（边界、各步减法、建议“减小 ION_SIZE / RTOS_ION_SIZE”），便于用户自助修正。

缺口提示：约束 3 里的 256M 边界同样写死。对 128/512MB 芯片需替换为对应 DRAM 边界， 否则校验会用错误基准误判——这是与 关联文档第 ④/⑦ 节呼应的关键修正点。

⑥UI 与状态反馈

沿用现有视觉语言（slate 暗色 + indigo 主色），关键控件集中在 MemoryTable 顶栏：

顶栏动作区

  • 重置 — 重新 loadMemoryRegions()
  • 校验内存（绿）— validateMemory，成功 3s toast
  • 保存并导出（靛）— exportDefconfig(sdkPath, chipType)
  • 新增区域 — 弹窗表单

三态反馈

  • error：红色条 + animate-shake，显示「布局校验错误: …」
  • validationSuccess：绿色条「校验成功，无重叠」
  • exportSuccess：靛色条「已同步导出至 defconfig」

编辑约束在 UI 上的体现

  • ION / H26X_BITSTREAM / H26X_ENC_BUFF / ISP_MEM_BASE 的起始地址只读（级联绑定），编辑弹窗中置灰并标注「只读/级联绑定」。
  • 系统内置区段不可删除；自定义区段可增删。
  • 右侧物理分布概念图实时反映 regions[]，未分配空间自动补齐 — 让“互踩/空洞”肉眼可见。
建议增强：校验返回的重叠区段名，可在右侧分布图中高亮标红对应两段，把“互踩”可视化定位，而不仅是文字报错。

⑦风险与增强建议

风险 / 缺口影响建议方案
导出未强制先校验可能把互踩配置写进 SDK在 exportDefconfig 内部先 await validateMemory()，失败即中止
直接覆写无备份写坏 defconfig 难恢复写前生成 <chip>_defconfig.bak / .config.bak；写失败回滚
DRAM 边界写死 256Mcv1841/cv1843 级联与约束误判引入 chipDramSize(chipType)，128/256/512MB 动态边界（呼应关联文档）
只写 SIZE 不触发再生成用户忘了 make memory-map，.h 未更新可选封装 Tauri 命令执行 make memory-map 并回读 .h 预览
defconfig 路径硬编码 cv184x其他芯片架构不通用路径中的 cv184x 由 chipType 推导 chip_arch（参考 boards_scan.py）
并发/路径非法sdkPath 为空时报错体验差已有前端兜底（提示先配置 SDK 路径），建议 Rust 侧再校验路径存在性
优先级：① 校验闸门（正确性）> ② 写前备份（安全）> ③ 多芯片边界（覆盖面）> ④ 一键再生成（体验）。

⑧实施清单

  • memoryStore.ts：exportDefconfig 起始处串入 validateMemory()，未过抛错、不 invoke 写盘
  • memoryStore.ts：把级联里的 0x90000000 改为 baseAddr + dramSize(chipType)
  • memory.rs：export_memory_defconfig 写前生成 .bak，fs::write 失败时回滚
  • memory.rs：validate_memory_constraints 的 256M 边界参数化（按 chipType）
  • memory.rs：defconfig 路径的 cv184x 段由 chip_arch 推导，去硬编码
  • UI：校验失败时在右侧分布图高亮互踩区段
  • （可选）新增 run_make_memory_map 命令，导出后一键重生成并回读 .h 预览
